# WS-3.1 Persistent Orchestrator Core Design

**Status:** Approved; adversarial review incorporated
**Date:** 2026-07-04  
**Intent package:** `ws-3.1-orchestrator-core`, revision 1  
**Approved intent hash:** `4414eae543d9dac8b1983f796593569d9abf97dfee1b8a06ef29b308e7b8337b`

## 1. Objective

Build the minimum persistent, domain-neutral service that owns canonical work-unit
lifecycle truth. Intent packages continue to define what and why. Workers execute one
authorized unit and submit evidence. Verifiers and humans evaluate evidence. Only the
orchestrator records canonical lifecycle outcomes.

WS-3.1 proves deterministic state, persistence, claims, authority gates, evidence
storage, attributable events, and equivalent API/CLI behavior. It does not dispatch
workers, automate package intake or decomposition, publish external factory events,
implement independent verification policy, deploy infrastructure, or merge pull
requests.

## 2. Governing boundaries

### 2.1 Canonical ownership

`intent-packages` remains canonical for:

- Package content and revision numbering.
- The package's exact content hash.
- Package lifecycle and human approval chain.
- The declared outcome, scope, authority, acceptance criteria, and evidence
  requirements.

The orchestrator is canonical for:

- Registered package-revision enforcement facts.
- Work-unit decomposition approval state.
- Work-unit readiness and lifecycle state.
- Claims, leases, attempts, dependencies, and authority holds.
- Realized evidence, AC adjudications, waivers, and work-unit approvals.
- Attributable lifecycle events.

GitHub, Linear, Todoist, PR comments, and Evidence Pack reports are projections or
execution/review surfaces. None owns lifecycle state.

### 2.2 Package representation

The orchestrator does not store a second editable package document. For each registered
revision it stores:

- Package ID and revision.
- Canonical content hash.
- Immutable source repository, path, and commit reference.
- Package approval proof and approving human identity.
- A normalized immutable enforcement snapshot containing only fields required for
  readiness, authorization, acceptance-criterion association, and verification
  boundaries.
- An authority fingerprint derived deterministically from the authority envelope.

The source reference and hash preserve provenance. The normalized snapshot makes
decisions reproducible if the source repository is temporarily unavailable. A new
package revision creates a new row; existing revisions never change.

WS-3.2 will implement automated immutable intake and decomposition proposal. WS-3.1
uses an authorized manual API/CLI registration path so its lifecycle can be tested
without preempting that workstream.

## 3. System shape

The application is a single FastAPI service and deployable container backed by
PostgreSQL 16.

It has four internal boundaries:

1. **Lifecycle kernel:** pure state graph, readiness evaluation, transition guards,
   actor-role authorization, authority comparison, and lease policy. It accepts an
   injected clock and does not depend on FastAPI or SQLAlchemy.
2. **Persistence layer:** SQLAlchemy models, focused repositories, and transaction
   services. PostgreSQL constraints enforce invariants that remain valid regardless of
   caller.
3. **Interfaces:** a REST API, a thin HTTP CLI, and a server-rendered Jinja/HTMX human
   review UI. Interfaces call the same application services and never reproduce
   lifecycle logic.
4. **Identity boundary:** Alobar ID forward-auth and M2M credentials both resolve to a
   common authenticated actor context used by authorization and event attribution.

### 3.1 Request flow

1. Authentication resolves a registered actor and authority profile.
2. The interface parses the command and idempotency key.
3. An application service opens a transaction and locks the relevant aggregate.
4. The lifecycle kernel evaluates current facts and returns a decision or stable error.
5. The persistence layer writes the state mutation and an outbox event atomically.
6. The transaction commits.
7. The interface returns the new state and event ID.

An external event-publisher failure cannot affect lifecycle state because WS-3.1 does
not publish externally. WS-3.4 will consume the transactional outbox.

## 4. Persistent model

All primary keys use UUIDs generated by the service. Timestamps are timezone-aware UTC.
Human-readable IDs are separately unique where needed. Mutable rows carry an integer
version for optimistic concurrency in addition to transaction locking.

### 4.1 `work_packages`

Stable package identity:

- `id`
- `package_id` (unique)
- `source_repository`
- `created_at`

Package content and package lifecycle do not live here.

### 4.2 `work_package_revisions`

Immutable registration of one package revision:

- `id`
- `work_package_id`
- `revision`
- `content_hash`
- `source_path`
- `source_commit`
- `approved_by`
- `approved_at`
- `approval_event_id`
- `enforcement_snapshot`
- `authority_fingerprint`
- `registry_version`
- `registered_by`
- `registered_at`

Constraints:

- Unique `(work_package_id, revision)`.
- Unique `(work_package_id, content_hash)`.
- Revision is positive.
- Required source and approval fields are non-empty.
- PostgreSQL append-only triggers reject update and delete.

### 4.3 `work_units`

Canonical unit state and enforcement linkage:

- `id`
- `unit_key` (unique within package revision)
- `work_package_revision_id`
- `title`
- `outcome`
- `state`
- `decomposition_approved_by`
- `decomposition_approved_at`
- `required_capability`
- `authority_fingerprint`
- `authority_approval_id`
- `attempt_count`
- `max_attempts`
- `version`
- `created_at`
- `updated_at`

Constraints:

- Unique `(work_package_revision_id, unit_key)`.
- State is one declared state.
- Attempts are non-negative and do not exceed the approved limit.
- A unit cannot be `Ready` or later without approved decomposition metadata.
- Package revision and unit are immutable associations.

### 4.4 `dependencies`

Structured readiness inputs:

- `id`
- `work_unit_id`
- `kind`: `work_unit`, `external_system`, `pull_request`, or `decision`
- `required_state_or_condition`
- `depends_on_work_unit_id` for internal dependencies
- `external_ref` for external dependencies
- `status`: `pending`, `satisfied`, or `failed`
- `resolved_by`
- `resolved_at`
- `resolution_event_id`
- `detail`

Exactly one of the internal or external reference forms is present. A dependency cannot
be self-referential. Internal dependency cycles are rejected by the application service.
Resolution is attributable and event-backed.

### 4.5 `claims`

Retained attempt-bound lease history:

- `id`
- `work_unit_id`
- `attempt`
- `claimed_by`
- `lease_token_hash`
- `idempotency_key`
- `acquired_at`
- `renewed_at`
- `lease_expires_at`
- `released_at`
- `terminal_reason`

Locking guarantees at most one effective live claim for a unit. Claim acquisition locks
the work unit, checks the previous claim against database transaction time, increments
the attempt when reclaiming, and creates a new row. Renewal and release update only the
current claim's lease metadata. Expired and terminal claim rows remain history and are
never reused for another attempt.

The raw lease token is returned once and never stored. Worker mutations require the
matching actor, attempt, and token hash. A stale worker cannot start, renew, submit,
block, fail, or attach attempt-scoped evidence.

### 4.6 `approvals`

Typed human decisions:

- `id`
- `subject_type`: `work_unit`, `authority`, `retry`, or `action`
- `subject_id`
- `subject_revision_or_fingerprint`
- `decision`: `approved` or `rejected`
- `approved_by`
- `reason`
- `created_at`
- `event_id`
- `idempotency_key`

The approver must resolve to an active registered human operator. Approval is always
bound to an immutable subject version or fingerprint.

### 4.7 `evidence`

Append-only realized evidence:

- `id`
- `work_package_revision_id`
- `work_unit_id`
- `ac_id`
- `attempt`
- `evidence_type`
- `stable_ref`
- `payload`
- `source_revision`
- `recorded_by`
- `recorded_at`
- `event_id`
- `idempotency_key`
- `supersedes_evidence_id`

At least one of `stable_ref` or `payload` is present. Supersession must target evidence
for the same package revision, work unit, and AC. PostgreSQL append-only triggers reject
update and delete. Query services identify current evidence by following supersession
links while retaining the full chain.

Standing-context, skills, and standards versions may be recorded in the structured
payload. WS-3.3 makes those fields mandatory at worker preflight.

### 4.8 `adjudications`

Explicit AC outcomes:

- `id`
- `work_package_revision_id`
- `work_unit_id`
- `ac_id`
- `outcome`: `passed`, `failed`, `waived`, or `not_applicable`
- `evidence_id`
- `decided_by`
- `decided_at`
- `rationale`
- `failed_evidence_id`
- `risk`
- `follow_up`
- `scope`
- `expires_at`
- `event_id`
- `supersedes_adjudication_id`

PostgreSQL append-only triggers reject update and delete. A current outcome is the
terminal item in its supersession chain.

For `waived`, database and service guards require:

- A registered human `decided_by`.
- `failed_evidence_id`.
- Non-empty rationale, risk, and follow-up.
- Scope when the waiver is narrower than the entire AC.
- Expiry where time limits apply.

A worker cannot create an adjudication. Expired or out-of-scope waivers do not satisfy
completion guards.

### 4.9 `events`

Append-only local event and transactional outbox:

- `id`
- `occurred_at`
- `actor_id`
- `action`
- `subject_type`
- `subject_id`
- `from_state`
- `to_state`
- `payload`
- `correlation_id`
- `idempotency_key`

The lifecycle mutation and its event share one database transaction. WS-3.1 leaves
events undispatched. PostgreSQL append-only triggers reject update and delete. WS-3.4
will add a separate delivery table keyed to immutable event IDs and publish to
`factory-event/v1` idempotently.

## 5. State machine

### 5.1 States

- `Draft`
- `Ready`
- `Claimed`
- `Executing`
- `Blocked`
- `Awaiting Approval`
- `Submitted`
- `Verifying`
- `Awaiting Review`
- `Revision Required`
- `Completed`
- `Failed`
- `Cancelled`

### 5.2 Complete legal graph

Primary path:

```text
Draft → Ready → Claimed → Executing → Submitted → Verifying → Completed
```

Controlled edges:

```text
Claimed → Blocked | Awaiting Approval | Failed | Cancelled
Executing → Blocked | Awaiting Approval | Failed | Cancelled
Submitted → Revision Required | Awaiting Review | Failed | Completed
Submitted → Verifying
Verifying → Revision Required | Awaiting Review | Failed | Completed
Blocked → Ready
Awaiting Approval → Ready | Cancelled
Awaiting Review → Completed | Revision Required
Revision Required → Ready
Failed → Ready | Cancelled
```

`Submitted → Completed` is legal only for an authorized verifier when all completion
guards pass. A worker invoking the same edge is denied. This preserves the canonical
graph while preventing worker-declared completion.

Every other ordered state pair is invalid. Exhaustive tests derive the complement of the
legal graph and explicitly retain regression cases for:

- `Draft → Executing`
- `Ready → Completed`
- `Executing → Completed`
- `Blocked → Completed`
- `Awaiting Approval → Executing` without recorded approval

### 5.3 Readiness

Readiness evaluation returns a structured decision:

- `ready`: every deterministic prerequisite is satisfied.
- `blocked`: a declared dependency or required input is unresolved.
- `not_authorized`: required package/decomposition/authority approval is absent or the
  prospective actor lacks capability.

A unit may transition `Draft → Ready` or return to `Ready` only when:

- Its package revision is immutably registered with valid approval proof.
- Its decomposition is human-approved.
- Every required dependency is satisfied.
- Its authority fingerprint is covered by an exact human approval.
- Its required capability is available to an eligible actor class.
- Its attempt budget is not exhausted.

The response includes reason codes and references to the facts producing the decision.

### 5.4 Authority expansion

Authority fingerprints are deterministic normalized hashes. A new fingerprint is
compared with the approved authority:

- Capabilities form the restriction order
  `prohibited < requires_approval < allowed`.
- A change is non-expanding only when every capability remains equal or moves toward
  `prohibited`, and every numeric budget remains equal or decreases.
- Adding an allowed capability, making any capability less restrictive, increasing a
  budget, or removing a finite budget is expansion.
- Unknown fields and comparisons that cannot prove non-expansion fail closed as
  expansion.
- Expansion invalidates readiness until a human approval binds to the new fingerprint.

WS-3.1 does not implement WS-3.3 same-scope skill-subscription semantics.

## 6. Claims and leases

- Default lease: 15 minutes.
- Expected renewal cadence: every 5 minutes.
- Clock: PostgreSQL transaction time for acquisition, renewal, and expiry decisions.
- Maximum attempts: three by default, constrained by the approved package/unit budget.
- Acquisition: atomic, exclusive, idempotent, and legal only from `Ready`.
- Renewal: legal only for the same actor, attempt, and lease token before expiry.
- Expiry: does not rewrite history; it makes the claim ineffective.
- Reclaim: locks the unit, confirms expiry, records
  `Claimed|Executing → Failed → Ready → Claimed` as three attributable transitions in
  one transaction, creates a new claim, and increments the attempt. This uses only
  declared legal edges and records the abandoned attempt honestly.
- Exhaustion: the unit becomes `Failed`.
- Retry after exhaustion: requires a human retry approval bound to the unit version and
  a new approved attempt limit or one-time retry grant.

The first claim request for an idempotency key owns that result. Repeating the same
request returns the same claim. Reusing the key with different input is a conflict.

## 7. Identity and authorization

### 7.1 Actor context

Every request resolves:

- Stable actor ID.
- Actor type: human, worker, verifier, or system.
- Registry status and authority profile.
- Credential key ID or human session provenance.
- Correlation ID.

Unknown, inactive, reserved, or ambiguous identities fail closed.

The identity boundary uses a registry adapter. Local development reads a configured
Phase-1 registry checkout. Container builds embed a generated actor/authority bundle
from an exact `security-standards` revision. Startup validates the bundle schema and
every credential-key mapping. Registry changes require a rebuilt image; events record
the registry version used for authorization.

### 7.2 Human UI

The service accepts Alobar ID forward-auth headers only from its configured proxy trust
boundary. Direct clients cannot manufacture identity through those headers. The mapped
human identity must be an active registry human operator. WS-3.1 expects `devon`.

Mutating form requests require CSRF protection and explicit confirmation for approval,
cancellation, review outcome, and retry.

### 7.3 API and CLI

M2M bearer credentials map one-to-one to a registered Phase-1 `agent_id`. Credential
material remains in BWS/runtime configuration. The application stores only the stable
actor ID, credential key ID, and registry version in audit facts.

The CLI is a thin HTTP client. It does not import the lifecycle kernel or connect
directly to PostgreSQL.

### 7.4 Role capabilities

- Worker: claim, renew, start, block, request approval, fail its attempt, append
  evidence, and submit.
- Verifier: begin verification, append verification evidence, and adjudicate non-waiver
  outcomes when authorized.
- Human: supply sensitive approval, waiver, review outcome, cancellation, and retry.
- System: evaluate deterministic readiness and record system transitions.

Workers cannot approve decomposition, expand authority, waive an AC, set `Completed`, or
merge a pull request.

## 8. Interfaces

### 8.1 REST API

The API covers:

- Register package revision and approved decomposition for WS-3.1 manual operation.
- Inspect readiness with structured reasons.
- Claim, renew, release, and inspect leases.
- Start, block, request approval, approve/reject, submit, verify, review, complete, fail,
  retry, and cancel through authorized transition commands.
- Append and inspect evidence.
- Append and inspect adjudications.
- Inspect dependencies, approvals, and event history.
- Liveness and readiness health.

Every mutation accepts an idempotency key and expected aggregate version. Errors use a
stable body containing:

- Machine code.
- Human explanation.
- Current state and version.
- Relevant reason facts.
- Permitted recovery action where one exists.

### 8.2 CLI

The CLI mirrors API commands and error codes. It supports machine-readable JSON and a
concise human display. Contract tests invoke API and CLI paths against the same
scenarios and compare semantic results.

### 8.3 Human review UI

The UI is deliberately small:

- Queue grouped by state and readiness result.
- Work-unit detail showing package revision/hash, authority, dependencies, claim and
  attempt state, evidence, adjudications, approvals, and event history.
- Human approval/rejection.
- Human review outcome.
- Cancellation.
- Authorized retry.

Unit creation, package registration, worker operations, and bulk administration remain
API/CLI-only.

### 8.4 Evidence Pack

A read-only projection renders package revision, unit state, actors, authority,
acceptance criteria, current and superseded evidence, adjudications, waivers,
dependencies, checks, approvals, and events. The projection is not canonical and cannot
be edited independently.

## 9. Health and migration behavior

- `/health/live`: process liveness only; does not require PostgreSQL.
- `/health/ready`: verifies database connectivity and that the database is at the
  expected Alembic head.
- Migration command: explicit and separate from web-process startup.
- Empty-database test: upgrades from base to head.
- Drift test: detects schema behind/ahead or multiple unexpected heads.

Health responses expose only status and stable reason codes, not credentials, database
addresses, or internal exception details.

## 10. Error and concurrency handling

- Aggregate mutations lock the work-unit row.
- Claim acquisition additionally evaluates effective claims using database time.
- Expected versions prevent lost updates at interface boundaries.
- Database constraints are translated to stable domain conflicts.
- State and event writes are one transaction.
- Failed transactions produce neither mutation nor event.
- Idempotency records/results are transaction-bound to their mutation.
- Retryable serialization/deadlock failures are bounded and observable.
- Application exceptions do not expose SQL or secret-bearing configuration.

## 11. Testing strategy

### 11.1 Pure kernel tests

- Every legal graph edge.
- Every invalid state pair.
- Transition guard and role combinations.
- Readiness reason precedence and explainability.
- Authority expansion comparison.
- Lease policy using injected clocks.

### 11.2 PostgreSQL integration tests

- Alembic empty-to-head and drift behavior.
- Database constraints.
- Database-enforced append-only package revisions, evidence, adjudications, and events.
- Two concurrent claims: exactly one winner.
- Idempotent duplicate claim.
- Renewal ownership and expiry boundaries.
- Expired-lease reclaim and attempt increment.
- Stale token and stale attempt rejection.
- Attempt exhaustion and human retry.
- State/event atomicity under injected failure.
- Evidence and adjudication append-only/supersession rules.

SQLite is unsupported because it cannot prove the required PostgreSQL locking semantics.

### 11.3 Interface and security tests

- API/CLI semantic parity.
- Stable error bodies.
- M2M identity mapping and fail-closed cases.
- Forward-auth trust boundary and spoofing rejection.
- CSRF on human mutations.
- Worker prohibition on completion and waivers.
- Health endpoint disclosure checks.
- No automatic merge or production mutation path.

### 11.4 Human review

Devon reviews:

- Rendered queue and detail screens.
- Approval/review/cancel/retry behavior.
- Evidence Pack readability.
- The final architecture and security review.

## 12. Development and deployment boundaries

Local development uses PostgreSQL 16 through Docker Compose. No tracked environment file
contains credentials. Runtime secret retrieval follows the portfolio BWS standard and
will be designed before any secret or deployment work.

The application is compatible with the Flavor-B pattern:

- Python 3.12 FastAPI service.
- One immutable container exposing port 8000.
- GHCR image.
- Explicit Alembic migration step.
- Separate managed PostgreSQL database.
- Alobar ID forward-auth for the UI.
- M2M authentication for API/CLI.
- A generated, version-pinned Phase-1 actor/authority registry bundle containing no
  credentials.

WS-3.1 does not mutate infrastructure. Deployment requires a separate approved
`infrastructure-change` package and a fresh session. The approved target is:

```text
Mac mini
└── OrbStack
    └── Ubuntu virtual machine
        └── development Coolify instance
            ├── orchestrator application
            └── managed PostgreSQL 16 database
```

That deployment package must consult InfraOps planning capability before applying
changes. The current MCP discovery exposed direct read and mutation tools but no
planner, so tool availability must be resolved during deployment planning rather than
silently substituting direct mutation.

## 13. Explicit non-goals

- Automated package intake or decomposition approval (WS-3.2).
- Standing-context preflight, same-scope subscription semantics, protocol suite, or
  status ledger (WS-3.3).
- External `factory-event/v1` publication (WS-3.4).
- Automatic dispatch or factory runners (Phase 4).
- Independent verifier policy (Phase 5).
- Production observation or learning (Phase 6).
- Tracker-owned lifecycle state.
- Automatic merge.
- Production infrastructure mutation.
- A listing-specific profile or software-only core assumptions.
- Broad changes to existing foundation repositories.

## 14. Implementation sequence

1. Establish repository quality, security, test, and PostgreSQL harnesses.
2. Implement the pure lifecycle kernel and exhaustive graph tests.
3. Add the first migration and immutable package/work-unit/dependency models.
4. Implement readiness and authority approval.
5. Implement atomic claims, leases, expiry, reclaim, and attempts.
6. Implement evidence, adjudications, approvals, and transactional events.
7. Add actor context, M2M auth, and forward-auth boundary.
8. Add REST commands and stable errors.
9. Add the thin CLI and API/CLI contract tests.
10. Add the minimal human UI and Evidence Pack.
11. Run the full local gate, adversarial review, security scan, and whole-branch review.
12. Open a draft PR and wait for the exact named `Quality` check.

Devon alone merges.

## 15. Acceptance traceability

The implementation plan must map each task and test to intent-package AC-001 through
AC-014. No criterion may be inferred as passed. Realized evidence and an explicit
outcome are required. Any deviation must block or follow the approved waiver model;
historical failures remain historical.
