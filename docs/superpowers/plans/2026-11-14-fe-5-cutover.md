## The switch

Every prep pull request must change nothing when it merges. The Mac lanes run the orchestrator main
tree and the other checkouts by activation (`run-work-carrier.sh` line 146; `run-bump-proposer.sh`
line 163; `factory-events-nightly.sh` line 35). A set password selects the database chain
(`chain.py` lines 46-49), and `import-file` refuses a non-empty chain (`db.py` line 181). So a
launcher that fetched a password on merge would append before the import, or read an empty chain.

A Keychain item's existence can't serve as the switch:

- Two of the five holders already have their Keychain items, and both already hold their grants:
  `BWS_ACCESS_TOKEN_SDS_HQ` (`sds-hq`) and `BWS_ACCESS_TOKEN_SDS` (`sds-operator`, which keeps its
  read-secret grant until 3f-2).
- The session's item must exist before the import, which comes before the other holders switch.

**The switch is one non-secret settings file, `~/.factory/chain-db.env`.** It holds exactly three
lines, in `KEY=value` form with no quoting:

```
FACTORY_EVENTS_DB_HOST=100.92.138.19
FACTORY_EVENTS_DB_PORT=15432
FACTORY_EVENTS_DB_NAME=postgres
```

Every holder's launcher behaves as follows:

- **File absent:** behave as on `main` today. Fetch no password, and set no chain variable.
- **File present:** read exactly the three keys. Refuse an unknown key, a missing key, or a file
  that isn't a regular file. Fetch the holder's password through the holder's own account. Pass
  the password and the three settings only to the child that needs them. If any step fails, fail
  the pass visibly, through `sds_outcome_fail`, `fail`, or a `Refusal`. Never fall back to the
  file (Code Brain rule 4).

The file isn't `~/.factory/env`. The nightly sources that file with `set -a`, and it carries
`FACTORY_DB_DSN` (`factory-events-nightly.sh` lines 88-92), so other holders mustn't read it. HQ's
cycle runs under `env -i` and passes only `HQ_*` variables (sds-hq `bin/hq-env.sh` lines 37-51), so
no environment variable can reach the cycle as a switch; a file can. The file is outside every
repository, so HQ's checkout stop line doesn't apply to it (sds-hq `CLAUDE.md` lines 19-23). The
Mac backup copies `~/.factory` apart from `env` (vps-backup `backup-mini.sh` line 138), so the
file is backed up. It holds no secret.

**The import reads a staging copy, never the switch.** The act writes the same three lines to
`~/.factory/chain-db.env.pending` before the import (act step 5). Only the session wrapper's
`import-file` reads that path, and the wrapper refuses `import-file` while `chain-db.env` exists.
After the seal, the act runs `mv chain-db.env.pending chain-db.env` (act step 9). That `mv` is
amendment 7's "set each holder's switch", in the ADR's order. It also means no `approve` can
append to the empty chain before the import: with a live switch, one such append would make the
import refuse, and the trigger would keep the row.

**After the removal pull requests land, there's no file mode.** Without the file, a holder fetches
nothing, and its child refuses: `emit` and `verify` refuse with no password (removal PR R-SS), and
both readers refuse (R-IP, R-OR). That's fail-closed. A follow-up makes each launcher itself fail
by name when the file is absent (follow-up 2).

### What the act doesn't prove before step 10

Step 10 merges the removals before any scheduled holder has run under its own token. Each
holder's launcher is covered by its prep PR's stub tests, not a live run. A non-appending live
proof exists only for the carrier: a bare pass reads the chain, but only when an approved record is
queued. The nightly's deployed script can't run one stage alone, and the cycle and the bump
proposer prove themselves only by approving. So the act proves each holder at its first run
(steps 12 to 14), after the point of no return. A holder that fails there is fixed forward, and its
check pages.

### What rolls back after the rollback point

- **Step 7 (seal):** `mv` back and `chmod 0644` restore the file, and the steps at **RP** apply.
- **Step 8 (P-VB merged):** a revert pull request restores the backup check.
- **Step 9 (switch set):** `mv` the file back to `.pending`. No holder has run, so nothing has
  appended, and the step-7 rollback still applies.
- **From step 10:** nothing rolls back. The removal commits drop the file mode from every reader
  and writer. A revert pull request would restore code, but not a chain the file no longer holds.
- **From the first append** (the nightly's `adapt` at step 12): the database chain has events the
  file doesn't. Nothing rolls back, and a failure is fixed forward.

## Open questions

The ADRs don't settle these. Questions 1 to 3 go to Devon, and HQ queues them. HQ settled
questions 4 to 8 as its own choices, and each one records the choice.

1. **To Devon: `check_chain`'s role in database mode (sds-hq).** The cycle's retry guard (sds-hq
   `standing_approve.py` lines 392-404) reads the file. After the seal it returns silently,
   because the file is absent. HQ holds only the append password (amendment 25 item 3). The append
   role can `SELECT` (amendment 24 item 3), and the nightly already verifies under it (`chain.py`
   lines 72-77). D-44 B names the work carrier as the chain's only reader of the read password.
   Choose one:
   - The guard reads under the append role.
   - The guard refuses in database mode.
   - The guard goes.
2. **To Devon: re-running an import after a rollback.** The trigger refuses `DELETE` and `TRUNCATE`
   for every role, and `import-file` refuses a non-empty chain. Amendment 24 item 3 limits the owner
   to FE-4's setup acts. A rollback after a successful import leaves the database holding a copy
   that a retry can't replace without an owner act the ADRs don't name. One option is the owner
   dropping and re-running `db_setup` in an announced act. Whether `db_setup` re-runs on a populated
   schema is unverified.
3. **To Devon: the VPS verify.** Amendment 7 asks for "one `verify` on each machine". No VPS process
   holds either password until 3f-2's carrier container. One option is to make the VPS verify part
   of 3f-2's cut-over. Another is to name a one-time VPS verify identity.
4. **Settled by HQ: names this plan proposes.** The ADRs name none of these:
   - The switch file, `~/.factory/chain-db.env`, and its staging copy `chain-db.env.pending`.
   - The import's fetch account, `factory-events-session`. D-46 A names none, and amendment 25
     item 4 allows only an account item 3 already grants. This is the account that serves
     interactive sessions.
   - The archive, `~/.factory/events.sealed.jsonl`.
   - The three Keychain items, `BWS_ACCESS_TOKEN_FACTORY_EVENTS_SESSION`,
     `BWS_ACCESS_TOKEN_FACTORY_EVENTS_NIGHTLY` and `BWS_ACCESS_TOKEN_BUMP_PROPOSER`.
   - The wrapper's home in the orchestrator.

   HQ's choice: the import fetches under `factory-events-session` (amendment 25 item 4). The other
   names stand as this plan proposes them.
5. **Settled by HQ: the bump-proposer token's timing.** Amendment 25 item 3 has the Mac launcher
   read the `bump-proposer` account's token from its own Keychain item until the lane moves. G-59's
   page (step 5) says that account's token comes with the lane's mint sitting, not FE-5. This plan
   mints it in step 0. If the mint waits, the bump proposer stays disabled from step 13 until its
   token exists, because without a password it can't approve after R-SS. HQ's choice: the token is
   minted in FE-5 step 0 (amendment 25 item 3). The G-59 deferral was HQ's own text, not an ADR
   term.
6. **Settled by HQ: the secrets' registry rows.** Amendment 24 item 11 puts one
   `.cred-consumers.toml` row per secret in the orchestrator, with no rotation class "yet", and
   amendment 24's open item (ADR-0055 line 3516) leaves the class to FE-4, an HQ act. A row can't
   omit it: infraops `cred-consumers.ts` line 207 throws on a row with no `class`. HQ's choice:
   class `postgres-role-password` with `rotated_by_sds = false`, as P-OR-1 writes it.
7. **Settled by HQ: the rotation proposer's emits.** From step 11, its `revise` and `transition`
   emits fail and record `event_id` None (amendment 24 item 5). That's by design. This plan pauses
   it through the act only so it doesn't recreate `events.jsonl` between the seal and the removal's
   activation. No question is open about the design. HQ's choice: it's operational, and the pause
   stays.
8. **Settled by HQ: whether a session may read the chain.** Amendment 25 item 1 took chain reads
   away from every hand path, and amendment 25 item 3 gives `factory-events-session` the append
   password to run `approve`. D-46 A adds one import. A wrapper `verify` would make interactive
   sessions a chain reader under the append role, which the ADRs don't name. This plan doesn't use
   one: the import's own head check (step 6) and the nightly's own verify under its own token (step
   12) do the checks. HQ's choice: no session `verify` (D-44 B; amendment 25 item 1).
